## 3. Contextual Prompt Enrichment — ADOPT / CANONICAL_DESIGN

The child SHALL NOT be required to learn or compose prompt-engineering formulas in order to receive useful Guide help.

Canonical internal flow candidate becomes active design:
`RAW REQUEST → CONTEXT ENRICHMENT → INTENT → RESPONSE CONTRACT → EXECUTION → CHECK`

Context enrichment may use only already-authorized/relevant context such as:
- current subject/problem/stage
- current task/session/lap where applicable
- what the child already tried or reported
- age/language level
- applicable Guide/Subject/Planner state

Hard:
- enrich silently; do not expose prompt-engineering burden to the child.
- deterministic resolver/rules first when sufficient.
- AI only when ambiguity materially benefits.
- context enrichment SHALL NOT manufacture facts, diagnosis, surveillance evidence or hidden authority.
- Guide remains helper/ally; it does not absorb Subject interpretation or MAIN allocation authority.

## 4. Context-specific Response Contract — ADOPT / CANONICAL_DESIGN

Guide response shape SHALL adapt to learning context rather than use one generic chat style.

Active response contracts:
- `FOCUS`: brief, actionable, normally 1–2 sentences / one hint at a time; return attention to the task.
- `BLOCKED / HELP`: identify the specific blockage if known → minimum useful hint → next hint/step only as needed.
- `CONCEPT QUESTION`: core concept in easy words → familiar example/connection → brief understanding check when useful.
- `HOMEWORK FINAL ANSWER REQUEST`: method/concept/hint; do not write the final homework answer on the child's behalf.
- `WAITING_FOR_PARENT`: route clearly without blame or implying child failure.
- `COMPLETION / RETURN`: brief acknowledgement → next action; avoid inflated praise.

These inherit existing Answer First, Silence by Default, Stuck Detection ≠ Judgment, HELP ≠ CHECK and child-ownership rules.

## 5. Learning Representation capability — ADOPT / ADJUST

Do NOT create a competing independent AI authority named “Learning Representation Engine”.

Adopt it as a capability/responsibility inside Learning Master / Subject interpretation, with Guide rendering/communication support where applicable.

Purpose:
Transform confirmed source learning material, concept, error or task into the representation most useful for understanding/recall/execution.

Candidate representation modes:
- one-line explanation
- comparison / contrast
- sequence / timeline
- grouping / category
- example / analogy
- progressive hint
- visual cue / anchor
- exploration map

Responsibility boundary:
- `Learning Master / Subject` = interpret learning meaning + choose/recommend representation.
- `Planner / MAIN` = allocate amount/date/order; does not invent pedagogy from visual format.
- `Ready` = execute/display the confirmed task/representation within session context.
- `Hide & Seek` = memory/discrimination/recall specialist; may realize Confusion Set learning.
- `Snap & Pop` = thought/expression specialist.
- `Guide` = contextual communication/interaction across the family; does not become a second Subject Master.

Cost order:
`DETERMINISTIC / LOCAL → CACHED / REUSED → AI ONLY WHEN MATERIALLY BENEFICIAL`

## 6. Confusion Set Learning — ADOPT / CANONICAL_DESIGN

Where learning errors are meaningfully contrastive, the system may group confusable items and train the contrast itself rather than treating every miss as an isolated item.

Candidate flow:
`CONFUSABLE SET DETECTED → SIDE-BY-SIDE CONTRAST → DISTINCTIVE CUE → RECOGNIZE/SELECT → RETRIEVE/PRODUCE → CONTEXT USE → RETRACE`

Examples may include visually/phonologically/semantically confusable words or symbols, but examples are not universal rules.

Hard:
- do not force every error into a confusion set.
- grouping requires subject/learning evidence, not superficial similarity alone.
- Hide & Seek is the primary functional-app realization candidate for vocabulary discrimination/recall.
- cumulative weak-item/CODE RED/RETRACE lineage remains protected.
- exact detection thresholds and adaptive weights remain HOLD until validated.

## 7. Visual Chunk / Sequence / Hierarchy / Anchor — ADOPT / CANONICAL_DESIGN

Learning visuals SHALL use information structure, not decorative imagery alone.

Active design principle:
`CHUNK + SEQUENCE + HIERARCHY + VISUAL ANCHOR`

Useful pattern where appropriate:
`large category / whole → smaller units → meaningful visual anchor → short keyword → repeatable/recallable structure`

For Ready this reinforces, but does not replace, the existing hierarchy:
`WEEK MAP → DAY MAP → TODAY EXPEDITION MAP → FOCUS CLOCK`

Hard:
- image/icon presence alone does not constitute visual learning.
- do not copy social-media/Instagram card aesthetics as product UI.
- final Ready schedule remains a spatial/information map, not white cards placed over an island background.
- representation choice follows learning meaning and task purpose; visual format is not an authority source.
