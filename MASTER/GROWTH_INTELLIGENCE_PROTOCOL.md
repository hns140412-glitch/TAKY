# TAKY GROWTH INTELLIGENCE PROTOCOL

Status: REV_00 / CANONICAL OPERATIONAL PROTOCOL
Rule ID: TKY-GROWTH-001
Role: Turn external engineering ecosystems and internal execution evidence into localized, testable, reusable growth without bloating GRAND MASTER or copying external systems.
Authority: TAKY / GRAND MASTER > this protocol > lower-layer growth backlogs / project experiments.
Related: `MASTER/OUTCOME_OPTIMIZATION_PROTOCOL.md`, `MASTER/CONVERSATION_TO_SYSTEM_PROTOCOL.md`, `MASTER/ENGINEERING_EXECUTION_PROFILE_PROTOCOL.md`, `MASTER/UI_REFERENCE_PROTOCOL.md`.

## 0. Core principle — HARD LOCK

TAKY must improve from use and research, not merely accumulate rules.

`MORE POLICY != MORE CAPABILITY`
`POPULAR REPOSITORY != CURRENT BEST`
`COMMUNITY CLAIM != VERIFIED FACT`
`EXTERNAL PATTERN != LOCAL AUTHORITY`
`GAP RECORDED != GAP SOLVED`
`VALIDATION PASS != SYSTEM GROWTH`

Default growth loop:

`INTERNAL REALITY + EXTERNAL ECOSYSTEM EVIDENCE
-> PATTERN / FAILURE EXTRACTION
-> TAKY GAP COMPARE
-> LOCALIZED CANDIDATE
-> EXPERIMENT / IMPLEMENTATION
-> OUTCOME + REGRESSION EVIDENCE
-> ADOPT / ADJUST / HOLD / REJECT
-> CURRENT_BEST / FRONTIER UPDATE`

## 1. GitHub ecosystem-first research

For software, mobile-web/PWA, tooling, orchestration, CI/CD and developer-workflow research, GitHub ecosystem evidence is the default external discovery surface when materially relevant.

Research SHOULD inspect the smallest sufficient mix of:
- repository architecture and implementation;
- README/docs/examples;
- Issues, including recurring failure reports;
- Pull Requests and review comments;
- Discussions and maintainer/community answers;
- releases, changelogs and migration history;
- CI/eval/benchmark structure;
- related official platform repositories and communities;
- adjacent platform communities such as Netlify, Supabase, Vercel, Cloudflare, WebKit/Chrome, PostgreSQL, Notion and other actually used infrastructure.

Official product/platform documentation remains the preferred authority for current supported behavior. Community evidence is operational/case evidence unless independently verified.

`GITHUB REPO ONLY != GITHUB ECOSYSTEM REVIEW`
`STAR COUNT ONLY != QUALITY REVIEW`

## 2. Source selection signals

Do not rank a source from popularity alone. Consider materially relevant signals such as:
- maintenance freshness;
- release/commit continuity;
- contributor depth;
- issue/PR interaction quality;
- maintainer responsiveness;
- documented failure and recovery history;
- benchmark/evaluation evidence;
- architecture clarity;
- production/real-world use evidence;
- license/compatibility;
- direct relevance to the current TAKY/project gap.

A mature failure discussion can be more useful than a highly starred README.

## 3. Deep-search execution contract

When the user requests `딥서치 / 심층서치 / GitHub 사례 조사` or equivalent, the primary output is discovery and improvement, not another generic policy list.

Default execution:

`QUESTION / TARGET
-> CURRENT TAKY/PROJECT BASELINE
-> BROAD EXTERNAL SEARCH
-> HIGH-SIGNAL CASE SELECTION
-> SUCCESS + FAILURE + EVOLUTION REVIEW
-> PRINCIPLE EXTRACTION
-> LOCAL GAP
-> CONCRETE IMPROVEMENT CANDIDATE
-> VALIDATION / EXPERIMENT ROUTE`

A useful deep-search result SHOULD identify:
- what was actually inspected;
- why each high-signal case matters;
- the pattern or failure mechanism;
- what TAKY/project already has;
- what is missing or weaker;
- what should be tried or changed;
- what evidence would prove improvement.

Do not replace this with a restatement of existing governance.

## 4. Pattern record

A material reusable finding SHOULD preserve:
- `pattern_id`;
- source pointer(s);
- source class;
- observed success/failure;
- why the pattern exists;
- problem/failure class addressed;
- trade-offs/new risks;
- TAKY/project comparison;
- localization candidate;
- target owner;
- experiment/implementation reference;
- outcome evidence;
- disposition;
- current-best/frontier/supersession state.

Recommended lifecycle:

`OBSERVED -> REPEATED -> PATTERN -> CANDIDATE -> LOCALIZED -> VALIDATED -> ADOPTED/CURRENT_BEST`

or

`... -> HOLD / REJECT / SUPERSEDED`.

## 5. Gap persistence and downstream inheritance — HARD LOCK

Material deficiencies discovered during central review SHALL NOT disappear when implementation moves to a child project.

A reusable or family-wide unresolved gap must be written to an owner-visible backlog/support artifact with:
- stable gap id;
- affected scope/apps;
- current evidence;
- priority;
- current state;
- improvement direction;
- acceptance/exit condition;
- owner/destination;
- source/research pointers when useful.

Lower apps SHALL check applicable OPEN/HOLD family growth gaps during planning or implementation and either:
- implement/validate them;
- explicitly map them to a later milestone;
- mark them not applicable with reason;
- or provide newer evidence that supersedes them.

`CENTRAL GAP DISCOVERED + NO DOWNSTREAM ROUTE = SILENT LOSS CANDIDATE`
`BACKLOG ITEM EXISTS != IMPLEMENTED`

## 6. Layer placement

Growth output must go to the smallest correct owner.

- GRAND MASTER: only cross-system invariants and growth-routing semantics.
- Growth protocol/support registry: reusable external-learning process and shared gaps.
- OS/Work OS: operational projection, queues, workspace behavior.
- Family/domain owner: shared capability gaps across related apps.
- Project owner: project-specific design/runtime/implementation.
- History: research/validation evidence.

Do not move every useful GitHub pattern into GRAND MASTER.

## 7. Mobile-web/PWA growth focus

For PWA/mobile-web work, external research and internal evidence SHOULD actively compare:
- service-worker lifecycle and update atomicity;
- app/SW/data-schema version compatibility;
- offline durable storage and recovery;
- outbox/idempotency/retry;
- conflict/version semantics;
- state snapshot vs event history;
- cross-app/session contract compatibility;
- browser/iOS installed-PWA behavior;
- deploy/preview/cache behavior;
- observability and failure recovery.

Project/device claims still require project-specific runtime/device evidence.

## 8. External side-effect learning

External calls such as deploys, hosted previews, paid APIs, agent runs and remote build actions are measurable resources.

Growth review SHOULD distinguish:
- local/deterministic work;
- CI/replay;
- external preview/build;
- production/release action;
- repeated/recovery calls.

Repeated external calls without new evidence are a workflow failure candidate. Optimize the evidence gained per external side effect, not merely the number of tool calls.

## 9. Outcome learning

A change is a growth improvement only when useful evidence supports a better outcome.

Possible measures, when applicable:
- repeated-failure reduction;
- regression reduction;
- recovery success;
- fewer user-debugging escalations;
- lower unnecessary external calls;
- lower rework;
- smaller/more focused diffs;
- higher implementation completion;
- better resume/context recovery;
- lower sync/update failure;
- better runtime/device success.

Metrics are evidence aids, not universal scorecards. Choose measures that fit the actual work.

## 10. C2S / reflection boundary

External research enters as reference/case evidence.

`EXTERNAL DISCOVERY -> REFERENCE_ONLY / EVIDENCE -> LOCAL CANDIDATE -> VALIDATE -> OWNER REFLECTION`

External material does not gain canonical authority from popularity or repetition alone. Material adopted growth conclusions feed C2S/owner reflection with provenance and explicit disposition.

## 11. Current-best evolution

TAKY should preserve both:
- `CURRENT_BEST`: the best validated operating pattern currently adopted for a scope;
- `FRONTIER`: credible next improvements not yet sufficiently validated.

New evidence may supersede CURRENT_BEST, but prior evidence and supersession lineage remain recoverable.

`REALITY LOCKED / POSSIBILITY OPEN / EVIDENCE DRIVEN / CONTINUOUSLY GROWING`.

END
