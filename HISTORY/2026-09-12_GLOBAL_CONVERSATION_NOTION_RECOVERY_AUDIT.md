## 3. Recovered recurring failure pattern

The repeated mechanism is not merely “context window limit.”

Observed recurring chain:

`USER COMMAND / PRIOR DECISION EXISTS`
`→ ASSISTANT USES TOO-NARROW RECOVERY OR REINTERPRETS SCOPE`
`→ ITEM DECLARED MISSING OR RESULT SCOPE SHRINKS`
`→ USER CORRECTS / SEARCHES / RE-UPLOADS / SCREENSHOTS`
`→ ITEM IS RECOVERED`
`→ LOCAL RULE OR PATCH IS ADDED`
`→ SAME FAILURE CLASS REAPPEARS IN A LATER CONVERSATION`

This is classified as a systemic execution/recovery problem when the mechanism repeats, not a set of unrelated one-off mistakes.

## 5. Root causes

### RC-01 Rule exists, execution gate not activated
TAKY already contained strong anti-omission, source recovery, latest-user-correction, traceability and NO USER-AS-QA rules. The failure repeatedly occurred because those rules were read/mentioned without being turned into a pre-result gate.

### RC-02 Negative-existence claims were under-governed
The old system had `KEYWORD MISS ≠ PRIOR DECISION ABSENCE`, but did not explicitly classify and fail:
- `FALSE_MISSING_DECLARATION`
- `USER_FORCED_RECOVERY`
- `POST_CORRECTION_REOCCURRENCE`.

### RC-03 `UNVERIFIED_SOURCE_COVERAGE` could become an over-broad escape hatch
It correctly protects against invented history, but without taxonomy it can blur the difference between truly inaccessible evidence and evidence TAKY simply failed to recover.

### RC-04 Conversation corrections were stored as isolated events, not recurrence patterns
The Context Ledger preserved individual corrections but lacked a first-class cross-conversation Pattern Event linking repeated failures to one regression mechanism.

### RC-05 Lesson capture did not guarantee regression prevention
TAKY could record History/lesson documents without proving the same historical failure would now be blocked.

## 11. Audit conclusion

The central defect is now classified as a cross-conversation realization failure:

`USER INTENT / PRIOR DECISION → RECOVERY + INTERPRETATION → EXECUTION CONTRACT → ACTUAL RESULT`

was repeatedly broken at recovery/interpretation, forcing the user to re-prove prior context and causing result scope to drift.

The correction is therefore not “store more memory” alone. It is:
- distinguish true unavailability from TAKY retrieval failure;
- forbid unsupported negative-existence claims;
- record user-forced recovery as a system failure signal;
- aggregate repeated corrections into recurrence patterns;
- require historical replay/regression evidence before claiming the pattern is solved;
- learn through evidence-backed, scoped, reversible lesson/rule/skill evolution rather than uncontrolled rule accumulation;
- return to selective context after the explicit forensic backfill so ordinary execution remains efficient.
