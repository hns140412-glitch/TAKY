## 0. What Alpha is

TAKY Alpha is the whole-system operating specification produced by integrating the validated Beta decisions, later verified corrections, product/app contracts, engine contracts, growth pipelines, runtime boundaries, failure lessons, and current OPEN/HOLD state into one executable mental model.

Alpha is not:
- a list of file pointers,
- a routing graph alone,
- a handoff bundle,
- a status promotion label,
- a replacement semantic owner for lower domains.

Alpha must let a future TAKY session answer three things without reconstructing dozens of files:
1. what the system is trying to achieve,
2. who owns each decision and how execution flows,
3. what is proven, open, held, or forbidden.

The governing cycle remains:

`HUMAN INTENT → THINK AGAIN → KEEP YOUR KEY → FIND A WAY / SOLVE → YOU'RE THE KEY → VERIFY / CORRECT / CONTINUE`

Hard execution principles:
- USER != DEBUGGER.
- BLOCKED != FAILED.
- ACCESS FAILURE != SOURCE ABSENCE.
- ONE PATH FAILED != DESIRED OUTCOME FAILED.
- VALIDATED != APPROVED != COMMITTED != RELEASED.
- CODED != RUNTIME_VERIFIED != DEVICE_VERIFIED != DEPLOYED != PRODUCTION_VERIFIED.
- CURRENT / HANDOFF / HISTORY are continuity surfaces, not semantic authority.
- More agents, more checks, and more documents do not equal more progress.

## 22. Failure-defense model learned from Beta

Alpha carries forward not only successful rules but the defensive responses learned from repeated failures.

### 22.1 Fragmented handoffs
Failure:
many LATEST/HANDOFF files compete and stale state reopens old work.

Defense:
namespace CURRENT first; Handoff is recovery index only; CLOSED is inherited unless contradictory evidence exists.

### 22.2 Pointer-only “completion”
Failure:
an app/engine name appears in a routing graph and is treated as integrated.

Defense:
structural coverage requires actual owner, inputs, flow, consumer/producer relations, runtime manifestation, evidence, OPEN/HOLD, and claim dimensions.

### 22.3 Validation replacing work
Failure:
repeated auditing consumes time/quota without improving the product.

Defense:
build/integrate first; run proportional checks; stop when evidence is sufficient.

### 22.4 Agent quota waste
Failure:
Codex/Claude repeatedly search, rerun tests, or repeat equivalent reviews.

Defense:
MINIMUM CALLS / MAXIMUM PREPARATION; deterministic local first; one bounded implementation call.

### 22.5 User becomes debugger
Failure:
system asks user to find files, reproduce state, or test routine failures that are recoverable internally.

Defense:
USER != DEBUGGER; recover/search/diagnose using available tools before asking for the smallest human-only decision.

### 22.6 UI “functional pass” mistaken for quality
Failure:
a file renders or accepts input, so poor visual output is called done.

Defense:
actual deliverable/rendered-result comparison is a separate quality gate.

### 22.7 Stale candidate promotion
Failure:
old branch/PR/Handoff is treated as current authority.

Defense:
refresh current main/owner; candidate remains candidate until explicit applicable promotion.

### 22.8 Runtime overclaim
Failure:
code/CI is described as device/deployment/production success.

Defense:
independent claim dimensions remain explicit and cannot self-promote.
