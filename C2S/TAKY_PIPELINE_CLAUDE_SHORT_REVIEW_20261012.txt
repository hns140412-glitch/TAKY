# TAKY 10단계 P0 독립 검토 (독립 검토 의견, 파일 미열람)

**전제:** 도구를 쓰지 않았습니다. 아래 내용은 질문에 적힌 구성요소와 세션 메모리에 기록된 내용만 근거로 합니다. 코드 사실은 모두 **UNVERIFIED**이며, 구현 전에 RECON으로 재확인해야 합니다.

## 1. 진단: 부족한 것은 노드가 아니라 간선(edge)입니다

- 부품은 이미 있습니다. 충분성 판정(`mining_goal_sufficiency.py`), 방향성 확장(`mining_source_directional_expansion.py`), 형성 규약(`FORMING_PROTOCOL.md`), 실행기(`runtime_orchestrator.py`), 검토 루프(`executor_review_loop.py`)가 있습니다.
- 빠진 것은 이 부품들을 **런타임에서 실제로 호출하고, 앞 단계 산출물의 해시를 다음 단계 입력으로 강제하는 연결**입니다.
- `supply_gate` 테스트가 끊겨 있다는 것은 증거 등급이 `isolated-test`에 머문다는 뜻입니다. 통합 실행 증거나 E2E 증거는 아닙니다.
- 알려진 delta 필터 버그(`action != REUSE_PREVIOUS_BLOCKS`)는 denylist 방식입니다. 그래서 `BLOCKS_PERIODIC_CONTENT_AUDIT` 같은 새 action이 그대로 통과합니다. 이것은 "콘텐츠가 없는데 진행되는" 전형적인 누수입니다. P0에서 가장 작고 가장 확실한 항목입니다.

## 2. P0 구현 경계

**P0에 포함 (최소 diff, 기존 파일 확장):**

1. **단계 전이 계약 1개.** 하나의 레코드 스키마로 정의합니다.
   - 필드: `phase`, `input_hash`, `output_hash`, `status`(PASS / BLOCKED / FAILED / UNVERIFIED), `evidence_class`(doc / isolated / integrated / e2e), `goal_id`
   - 새 엔진을 만들지 않고 `runtime_orchestrator.py`의 기존 `--record` 경로를 확장합니다.
2. **supply_gate를 오케스트레이터에 배선합니다.** Indexing·Forming 다음, Production 앞에 둡니다.
   - 공급 영수증이 없거나 해시가 맞지 않으면 Production은 시작하지 않습니다(fail-closed).
3. **delta 필터를 allowlist로 교체합니다.** 위치는 `RUN_TAKY_POST_COLLECT_PIPELINE.ps1`과 `TAKY_INCREMENTAL.js`입니다. 변경 후에는 `*_pass.json`/`*_fail.json` 픽스처를 둘 다 갱신합니다.
4. **Mining 종료 조건과 보충 루프를 연결합니다.** `goal_sufficiency`가 구조화된 gap 목록을 내보내고, `directional_expansion`은 **그 목록만** 입력으로 소비합니다.
   - 보충은 횟수와 예산(유료 API 0, 로컬/구독 경로만)에 상한을 둡니다.
   - 상한에 도달하면 `HOLD`로 종결합니다. 무한 재시도는 금지입니다.
5. **Forming은 검사기만 둡니다.** 출처, 날짜, 불확실성 보존 여부만 기계적으로 확인합니다. Forming 엔진을 새로 만들지 않습니다.
6. **Validation 단계에서 `executor_review_loop`를 호출합니다.** 승인은 정확한 산출물 해시에 묶습니다. 산출물이 바뀌면 승인은 무효입니다.
7. **E2E 픽스처 3개를 둡니다.** 작은 로컬 목표 1개로 다음을 검증합니다.
   - (a) 정상 통과
   - (b) 공급 부족 → 보충 → 상한 도달 → HOLD
   - (c) 중간 산출물 변경 → 해시 불일치 → 차단

**P0에서 제외:**
- Intent·Discovery 자동화
- Feedback → CURRENT 자동 승격
- 신규 LLM 호출이나 신규 에이전트
- CURRENT·MASTER 수정
- NotebookLM

## 3. 강한 반대 의견 (Contrary Review)

1. **상태기계가 이미 3개 있습니다.** `execution_state_engine`, `execution_checkpoint`, `runtime_orchestrator`입니다. 10단계 엔진을 새로 얹으면 "또 하나의 끊긴 엔진"이 될 가능성이 큽니다. 기존 오케스트레이터로 표현 가능한지부터 증명해야 합니다. 증명하지 못하면 P0는 "배선"이지 "구축"이 아닙니다.
2. **자기 영수증 문제.** 같은 스크립트가 만든 산출물과 영수증을 같은 스크립트가 검증하면 `AUTHOR == SOLE REVIEWER`입니다. 해시 바인딩은 변조는 막지만 **잘못된 내용 자체**는 막지 못합니다. 독립 검증 단계가 반드시 필요합니다.
3. **픽스처 통과는 형식 검증에 그칠 수 있습니다.** CI가 `pass → 0, fail → 비0`만 본다면 "형태가 맞음"만 증명합니다. P0의 PASS를 "E2E 성립"으로 보고하면 과장입니다. 증거 등급을 반드시 병기해야 합니다.
4. **충분성 지표는 조작되기 쉽습니다.** 개수나 커버리지 기반이면 중복·유사 출처로 채워도 통과합니다. 출처 다양성과 provenance 중복 제거가 없으면 gate는 장식이 됩니다.
5. **fail-closed 데드락과 비용 누수.** 공급 부족이 영구적이면 파이프라인이 멈춥니다. 반대로 보충 상한이 느슨하면 비용이 샙니다. 상한과 HOLD 종결이 필수입니다.
6. **권한 드리프트 위험.** 방향성 확장으로 들어온 외부 출처가 Forming을 거쳐 CURRENT처럼 소비되면 `SOURCE → EVIDENCE → … → governed promotion` 흐름을 우회합니다. 경계는 EVIDENCE로 고정해야 합니다.
7. **작업 트리가 지저분합니다.** 수정(M) 20여 개와 미추적(??) 다수가 섞여 있습니다. 이 상태에서 해시 바인딩이나 revision-bound 검증은 기준선이 불명확해서 의미가 약합니다. 브랜치명(`character-asset-behavior-separation`)도 이번 작업과 무관합니다. P0 착수 전에 기준 커밋을 정리해야 합니다(커밋/푸시는 사용자 승인 사항).
8. **"10단계 전체"를 목표로 삼는 것 자체가 위험합니다.** 실패 지점이 간선 몇 개라면 10단계 모델링은 과잉 설계입니다. 먼저 3번(필터 버그)과 2번(공급 gate 배선)만 하고, 실제 E2E로 새로운 누수가 나올 때만 확장하는 편이 낫습니다.

## 4. 판정

- **GO:** 필터 allowlist 교체, supply_gate 배선, 해시 바인딩 전이 레코드, E2E 픽스처 3개.
- **NO-GO:** 신규 10단계 엔진, 자동 승격, 유료 호출이 있는 보충 루프.
- **착수 순서:** RECON(위 UNVERIFIED 항목 확인) → 기준선 정리 → 필터 버그 수정과 회귀 → gate 배선 → E2E 3종 → 독립 검토(작성자 ≠ 검토자).
- **완료 보고 시:** 증거 등급(doc / isolated / integrated / e2e)을 항목별로 명시해야 합니다. 그렇지 않으면 "PASS"는 주장일 뿐입니다.
