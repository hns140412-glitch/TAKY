# LEARNING APP FAMILY VISUAL / MOCKUP INTEGRATION REGISTRY — 2026-09-22

Status: ACTIVE CROSS-APP VISUAL LINEAGE REGISTRY
Purpose: integrate UI shape, visual composition, mockup lineage and app-specific design maturity without forcing identical screens.

## 0. Core model

Family UI is managed in three layers:

### A. SHARED VISUAL DNA
Cross-app visual principles that should feel like one product family.

### B. REGIONAL DIALECT
Ready / Snap / Hide may express the same family language differently according to region and product job.

### C. SCREEN-SPECIFIC COMPOSITION
Each screen keeps its own task hierarchy, interaction density and runtime constraints.

Rule:
**SAME FAMILY ≠ SAME SCREEN.**
**DIFFERENT APP ≠ DIFFERENT DESIGN UNIVERSE.**

---

# 1. Shared Visual DNA

LOCK_CANDIDATE / cross-app target:

- one connected island world;
- high-density original illustration on world/regional surfaces;
- calm functional surfaces on task-heavy screens;
- character/crew rendered through runtime slots;
- no emoji-first UI language;
- no generic dashboard/card-wall;
- no decorative background that competes with the task;
- one dominant action per task screen;
- shared spatial depth and world-light logic;
- consistent exploration signage / route markers / location naming;
- child-readable typography hierarchy;
- clear icon + label for unfamiliar actions;
- badge visual family shared across apps;
- shared badge tier/star-grade semantics;
- result/share surfaces prioritize actual record over decoration;
- 390×844 phone baseline;
- reduced-motion equivalent;
- non-happy states designed as product states, not technical error pages.

Visual character:
**Living exploration world + calm action layer.**

This phrase describes family-level behavior, not a final art style lock.

---

# 2. Shared composition grammar

## WORLD / HOME surfaces
- environment occupies meaningful visual space;
- character can appear as part of environment;
- routes/regions are spatially understandable;
- content floats lightly over world;
- avoid opaque tile walls that hide geography.

## TASK surfaces
- primary task occupies visual center;
- environment recedes;
- background is atmosphere, not UI;
- fewer containers;
- crew reaction is contextual;
- keyboard/input readability wins.

## RESULT surfaces
- child artifact/result first;
- concise emotional closure;
- one next action;
- badge/history may appear if relevant;
- no reward explosion.

## RECORD / COLLECTION surfaces
- information first;
- world styling through section headers/material/illustration accents;
- no giant scenery behind dense content.

A screenshot/image is never self-authoritative.

## ACCEPTED means
The user accepted a material visual/composition decision AND it does not conflict with current product rules.

## REFERENCE means
Useful look/feel/composition evidence only.

## SUPERSEDED means
A newer accepted/corrected direction replaces it.

## REJECTED means
Known bad direction; must not be resurrected by future design work.

# 10. Visual freeze levels

### V0 — REFERENCE ONLY
Loose inspirations and external references.

### V1 — DIRECTION CANDIDATE
Visual concept has useful characteristics.

### V2 — COMPOSITION LOCK
Screen hierarchy/placement accepted, art can still change.

### V3 — VISUAL SYSTEM LOCK
Typography/surface/icon/spacing/motion language accepted.

### V4 — SCREEN FAMILY LOCK
Major screen set accepted together.

### V5 — FINAL VISUAL FREEZE
Ready for implementation mapping/regression.

Each app may be at a different level.

Current approximate status:
- Ready: V1–V2 in active productization; some share/product composition rules stronger.
- Hide: V2-ish for several screen families; final art not frozen.
- Snap: V1 / criteria-first; no final composition lock.

These are workflow statuses, not implementation percentages.

---

# 11. Rejected / regression-prone visual patterns

Family-wide reject candidates:
- white/card wall that erases island world;
- scenery fully obscured by opaque timetable tiles;
- generic forest wallpaper with no spatial function;
- fixed character pasted into every screen;
- character art dominating task input;
- every domain becoming a bottom-nav tab;
- separate visual universe per app;
- giant hero illustration on dense task screens;
- badge/gem/star visual collapse;
- excessive glassmorphism reducing readability;
- map as decorative image with no navigation meaning;
- generic gamification counters replacing story/history.

---

# 12. Central integration workflow

When app UI work changes:

1. app conversation creates/updates mockup or composition decision;
2. classify it V0–V5;
3. identify shared vs app-local visual DNA;
4. add decision packet to TAKY UI Decision Registry;
5. add mockup lineage entry here;
6. run cross-app visual regression review;
7. update other app pointers only if family-impacting;
8. do not automatically restyle other apps.

---

# 13. Cross-app review questions

For every candidate visual:

1. Does it still look like the same island family?
2. Is the app's region recognizable?
3. Is the task clearer than the decoration?
4. Is the same child/companion identity preserved?
5. Does it introduce a conflicting badge/gem/star language?
6. Does it contradict another app's accepted family visual rule?
7. Is this truly family-wide, or only app-local?
8. Does it revive a rejected/superseded mockup pattern?
9. Can the same visual grammar support non-happy states?
10. Does the screen still work at 390×844?
