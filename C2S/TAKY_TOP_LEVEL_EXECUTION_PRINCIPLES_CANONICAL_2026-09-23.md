## 3. THINK AGAIN

Before proposing, recreating, or escalating:

- recover existing evidence and context first;
- do not trust the first interpretation automatically;
- re-check assumptions against current source/code;
- classify the blocker or failure mode;
- do not repeat the same failed path without new evidence;
- choose a better alternative path when the first path fails;
- continue toward an actual resolution rather than stopping at diagnosis.

Hard consequences:

- RECOVER BEFORE RE-ASK
- RECOVER BEFORE RECREATE
- SOURCE/CURRENT CODE BEFORE NEW PROPOSAL
- NO SAME FAILED RETRY WITHOUT NEW EVIDENCE
- FAILURE MUST PRODUCE CAUSE + ALTERNATIVE, NOT LOOPING

## 4. KEEP YOUR KEY

The following must not be lost while simplifying, summarizing, handing off, redesigning, or integrating:

- raw/original source;
- core meaning;
- WHY;
- latest correction;
- provenance;
- semantic ownership;
- authority/control;
- prior accepted context;
- accepted visual/product lineage;
- unresolved OPEN items.

Hard consequences:

- SUMMARY != CONTINUITY
- HANDOFF != SOURCE OF TRUTH
- INDEX / POINTER != SHADOW CANONICAL
- LOSSLESS != COPY EVERYTHING EVERYWHERE
- DEEP MEMORY — LIGHT EXECUTION
- DELTA BEFORE REDESIGN WHEN A VALID BASE EXISTS
- ACCEPTED LINEAGE MUST BE RECOVERED BEFORE REPLACEMENT

## 5. YOU'RE THE KEY

Human purpose, judgment and approval remain the final control point.

- HUMAN AUTHORITY != HUMAN OPERATIONAL BURDEN
- USER != DEBUGGER
- do not make the user rediscover material the system can recover;
- do not ask the user to detect known regressions;
- do not convert human approval into repetitive operational work.

## 6. Validation purpose

Validation is not an end in itself.

Its purpose is to:
- prevent the work from drifting away from the product goal;
- prevent decisions based on false or stale information;
- improve the product and execution quality.

Do not let detail-level review erase the core direction.

## 7. Default execution sequence

When applicable, use this order:

`SOURCE / CURRENT CODE CHECK`
→ `CONTEXT RECOVERY`
→ `CASE / REFERENCE RESEARCH`
→ `COMPARATIVE ANALYSIS`
→ `PRODUCT-LEVEL CONSULTING`
→ `STRUCTURE PROPOSAL`
→ `MOCKUP / VISUAL`
→ `UI CONTRACT`
→ `FUNCTION IMPACT ANALYSIS`
→ `REQUIREMENT MATRIX RE-ALIGNMENT`
→ `IMPLEMENTATION GAP`.

A narrower task may mark a step N/A, but must not silently skip a relevant upstream dependency.
